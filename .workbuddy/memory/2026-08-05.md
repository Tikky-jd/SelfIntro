## AI 代理防盗用加固（CORS 白名单 + x-site-key 口令）
- 用户确认代理对**所有访客**开放（含第三方网站盗用风险），要求做两步加固：① CORS 白名单；② 访问口令。
- **CORS 白名单的关键坑**：FC 的 HTTP 触发器网关会**自动回显 Origin 并注入 `access-control-allow-origin` 头**，代码里设的 ACAO 被覆盖。最初只在 `out()` 里控制 ACAO，结果 evil Origin 预检仍返回 `ACAO: https://evil.example.com`，完全没拦住。
  → 真正的防线必须在**业务层**：`index.js` 顶部 `ALLOWED_ORIGINS = new Set(['https://tikky-jd.github.io'])`，对带 Origin 且不在白名单的 `/chat` 请求直接 `return out(403, ...)` 且**不转发上游**（不消耗讯飞额度）。验证：evil Origin + 正确口令 → 403；白名单内 + 正确口令 → 200。
- **访问口令 `x-site-key`**：生成随机 `SITE_KEY=385oFUEfTgnlpq8UEZ_tjs5aHIu0ANLA`，写入 FC 函数环境变量 `SITE_KEY`；前端 `config.js` 加 `AI_SITE_KEY`（同值），`AIChat.vue` 每次 `/chat` fetch 带上 `x-site-key` header。FC 端缺失/错误返回 403。
- `deploy.mjs` 改造为**合并式环境变量**：先 `client.getFunction` 读取 FC 上已有 `XFYUN_KEY` 再合并 `SITE_KEY` 写回，避免覆盖式清空已配密钥。
- 验证全部通过：正确口令+白名单 Origin→200；无/错口令→403；白名单外 Origin(含正确口令)→403 不转发；白名单内 Origin 预检→204+ACAO。前端 build 产物含 `x-site-key` 与 `AI_SITE_KEY` 值（常量被 minify 内联）。
- 推送：REST API commit `4e26c806`，Actions success；线上 bundle 已含 `x-site-key`/`385oFUEf...`。
- ⚠️ **如实告知用户**：纯静态站点里 `AI_SITE_KEY` 经 build 内联进公开 bundle，任何人看源码可得，此口令**只能提高盗用门槛而非强鉴权**——第三方浏览器网页调用会被业务层 origin 白名单挡住（403），但第三方服务端直连（读源码拿 key）仍能调。要彻底防需后端强鉴权，纯静态架构无法根治。
